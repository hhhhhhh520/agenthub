## 2. 本项问题

### 2.1 seq 分配

`src/lib/services/event-log.ts`

- `createEventLogger` 从 `agentProcessEvent` 的 DB max 初始化 `seq`。
- 每个 logger 自己 `++seq`。
- 同一 session 若有两个 logger，会分配相同 seq；`create` 唯一约束失败后被 `catch` 吞掉，事件丢失。
- 已发出的 SSE 帧带 seq，不能通过“冲突后重读 max+1 改号”修复；会破坏帧身份。

### 2.2 SSE 轮询重叠

`src/app/api/sessions/[id]/events/route.ts:93`

- `setInterval(async () => ...)` 没有 in-flight 保护。
- 慢查询超过 `pollMs` 时，下一轮会与上一轮重叠，可能重复发送/游标竞争。

已有能力：持久化、重放、前端 seq 去重、flush 5s 上限。不要重做。

## 3. 推荐最小修法

### seq

优先方案：**进程内 per-session seq 分配器**。

- 在同一进程内按 sessionId 共享 `currentSeq` 与初始化 Promise。
- `createEventLogger` 等待一次 DB max 初始化；并发创建共享同一个初始化 Promise。
- 初始化完成后同步 `++currentSeq`，不同 logger 不再从同一 max 各自起算。
- 写入仍按 logger 的异步串行队列；失败必须显式 warn/记录，不能静默吞掉。
- 不通过重读 max+1 重编号已返回给 SSE 的 seq。

如果发现仍有跨请求/跨实例冲突：

- 先判断是否超出 P2-12 范围；不要擅自改 Prisma schema。
- 若需要 DB 原子序列，先向用户说明 schema/迁移成本并取得同意。
- 不要恢复“冲突重读 max+1 改号”的表面修复。

### SSE 轮询

- 增加 `polling` 标志：上一轮未完成时，本轮直接 return。
- `try/finally` 复位，确保查询异常后下一轮仍能继续。
- 保留 cursor 单调推进；不要重复发送同一 seq。
- cleanup/abort 后不再发起新查询。
