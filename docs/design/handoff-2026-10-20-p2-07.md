## 2. 本项问题

`src/app/api/sessions/[id]/chat/route.ts`：

1. 约 line 28：拿锁前读取完整 session。
2. 约 line 32-39：用该快照做取消检查，并派生 `permissionMode`、`workDir`。
3. 约 line 45：`acquireSessionLock`；同一 session 的请求可能排队等待。
4. 拿锁后当前只复查取消/删除标记（约 line 61），没有重读 session。
5. 后续继续使用旧快照中的：
   - `session.phase` / `session.phaseStep` / `session.decisionTrace`（line 218）
   - `session.type`（line 206 等分支）
   - `permissionMode`（line 36）
   - `workDir`（line 37-39）

后果：请求 B 排队期间，请求 A 可能修改 `phase/phaseStep`、`permissionMode` 或 `projectDir`；B 拿锁后仍按旧值选 handler/权限/工作目录，也可能用旧 `decisionTrace` 写 trace。

## 3. 最小修法

- 拿锁前读取保留，用于 400/404 早退和廉价校验。
- 拿到锁后重新读取 session（建议完整字段；至少 `phase/phaseStep/decisionTrace/permissionMode/projectDir/type`）。
- 若重读返回 null：返回 404，外层 finally 必须释放锁。
- 重读后重新检查 `isSessionCancelled` / `isSessionDeleting`（删除中仍回 409）。
- 用 fresh session 重新派生 `permissionMode` / `workDir`，后续所有分支使用 fresh 值；不要再引用旧快照。
- 不改变现有锁语义：不要为提前 404 拿锁；不要并发读写；锁仍由现有 try/finally 释放。
- 不修改 `session-lock.ts` 的等待/超时/abort 语义。

## 4. 必须新增测试

建议加到 `tests/chat-lock-release.test.ts`，利用已有 deferred `acquireSessionLock`：

1. **权限/目录刷新**：初读 `permissionMode=default`、`projectDir=/old`；请求排队期间 DB 改为 `auto`、`/new`；拿锁后必须用新值。断言 `handleOrchestratorDecision` 收到新 `permissionMode`/`workDir`（或私聊分支 `handleDirectAgentChat` 收到新值）。
2. **phase/decisionTrace 刷新**：初读 `idle`，排队期间改为 `alignment/pm_confirm` 且 trace 更新；拿锁后传给 `handleOrchestratorDecision` 的 `sessionPhase` 必须是新值。
3. **等待期间会话被删**：拿锁后重读 null → 404，且 release 调用一次。
4. **取消/删除标记仍优先**：重读成功后仍返回 409，不创建消息。
5. 现有锁释放/取消/regenerate 测试保持全绿。

测试必须模拟“A 持锁并修改，B 排队后拿锁”的受控窗口，不能只测单次读取。
