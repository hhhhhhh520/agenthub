## 3. 采用的修法

使用“删除中”生命周期标记，未改 DB schema：

- 新增一个叶子模块（例如 `src/lib/session-lifecycle.ts`）或在 cancellation 中增加删除标记：
  - `markSessionDeleting(sessionId)`
  - `isSessionDeleting(sessionId)`
  - `clearSessionDeleting(sessionId)`
- DELETE：
  - 在 `requestSessionCancel` 之前 mark；
  - 只有删除成功后才 clear；
  - 404 / 409 / 清理异常等失败路径必须在 finally 清 mark，允许用户重试；
  - 删除成功路径也不要提前 clear 取消标记。
- stop：
  - 若 `isSessionDeleting(sessionId)`，不得 `clearSessionCancel`；
  - 返回明确状态（例如 `deleting: true` / 202），避免客户端把“停止成功”误认为会话仍可继续。
- chat：
  - 拿锁前和拿锁后都检查 `isSessionDeleting`（与现有 `isSessionCancelled` 检查并列）；
  - deleting 时回 409，不创建 user message、不启动执行、不写 Task。
- 不要用 chat session lock 串行化 stop/delete；stop 需要能打断持锁执行流。
- 如果选择“生命周期串行锁”而非删除标记，仍必须让新 chat 能观察到 deleting 状态；只串行 stop/delete 不够。

## 4. 已新增回归

1. 并发 stop + DELETE：DELETE 进入 deleting 后，stop 不得 `clearSessionCancel`。
2. deleting 期间新 chat：返回 409，且不调用 `message.create` / `handleOrchestratorDecision` / `executeSingleAgent`。
3. DELETE 失败（409 未确认退出 / 锁未释放）后清 deleting 标记；下一次 DELETE 可正常重试。
4. DELETE 成功后才清 deleting；删除后新 chat 返回 404，不启动执行。
5. 现有 stop/delete 顺序测试和 chat 锁释放测试保持全绿。

测试要使用受控 Promise/顺序断言，模拟“waitForSessionUnlock 已返回但 DELETE 尚未删库”的窗口，而不是只测单路由 happy path。
