## 1. 本项问题

`transitionPhase` 返回：

```ts
Promise<{ ok: boolean; nextState?: State; reason?: string }>
```

`ok:false` 表示 phase 未写入（非法转移、CAS 快照冲突超限、DB 失败）。当前有四处调用只 `await`，没有检查 `ok`，可能在 phase 未推进时继续发“成功/阶段已切换”事件，或继续执行依赖新 phase 的流程。

按当前代码，四处为：

1. `src/lib/services/alignment.ts:224`
   - `handlePMConfirm` 中 `align_confirm`
   - 失败后仍继续 `sendEvent phase_transition`、执行 PM prompt。

2. `src/lib/services/alignment.ts:606`
   - `handleAgentQA` 中 `align_qa`
   - 失败后仍继续读取 history、执行多 Agent Q&A。

3. `src/lib/services/execution.ts:828`
   - `allDone` 时 `transitionPhase(sessionId, 'done')`
   - 失败后仍继续发 `done`/成功总结，形成“任务完成但 phase 仍 execution”的假成功。

4. `src/lib/services/chat-router.ts:306`
   - `case 'done'` 中 `transitionPhase(sessionId, 'done', ...)`
   - 失败后仍发送“任务已完成”文本与 `done` 事件。

## 2. 期望行为

### 2.1 handlePMConfirm

`align_confirm` 写失败时：

- 发送 `error` 事件，包含 `reason`；
- 不要再发 `phase_transition`；
- 不要执行 PM prompt / Agent 调用；
- 直接 return。

### 2.2 handleAgentQA

`align_qa` 写失败时：

- 发送 `error` 事件，包含 `reason`；
- 不要再读取 history/执行多 Agent；
- 直接 return。

### 2.3 execution allDone

`done` 写失败时：

- 不能发送成功 `done` 或成功总结；
- 发送 `error`（说明任务已完成但阶段写入失败）并让调用方可见；
- 可参考现有 `awaiting_user_input` 语义（`content: 'escalate'`）让 UI 停下，但不要自行发明新的持久状态；
- 保持任务本身 completed 状态不变，不修改任务数据。

### 2.4 chat-router done

`done` 写失败时：

- 不发送成功文本；
- 不发送成功 `done` 事件；
- 发送 `error` +（按现有模式）`awaiting_user_input`；
- 结束该 case。

## 3. trace / recordTrace 约束

- `chat-router.ts` `case 'done'`：`done` 失败时只发 error + `awaiting_user_input: escalate`，不发成功文本/done。
- 保留 `recordTrace` 语义与 `transitionPhase` 的 CAS 拒绝回执，未改 schema。

### 回归与变异

- 新增四条失败回归：PM、QA、execution allDone、chat-router done。
